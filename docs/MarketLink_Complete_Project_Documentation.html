1. What this project is

MarketLink is a web app for farmers markets. Buyers look at markets and produce, reserve what they want, then pick it up at the stall and pay the farmer in cash (Rs). There is no courier and no card checkout on the site. That choice was deliberate: the market already works that way in real life, and the software only organises browsing, stock, and pickup timing.

Three kinds of signed-in users exist. Customers place pre-orders. Farmers manage stock and the order queue. Admins approve stalls, keep catalogues tidy, and pull reports. Guests can still browse and use a temporary cart without creating an account first.

2. Why we built it

At a busy weekend market it is easy to sell out of something popular, or to pack the wrong amounts. Paper lists do not travel well between phone calls and the stall. MarketLink keeps a shared picture of what is listed, what was reserved, and when the customer intends to arrive. Payment still happens face to face, so the project stays out of payment-gateway complexity.

3. Scope boundaries

  • Pay at the stall only. No Stripe, JazzCash, or similar in this build.
  • Pickup only. No delivery routes or driver screens.
  • A farmer must be approved before products show on the public catalogue.
  • Reviews are meant for completed pickups, not random visitors.

4. Tech choices (and why)

Laravel 11 was used because routing, auth, validation, and Blade templates already cover most of a multi-role site. MySQL holds the data. The public UI is Bootstrap 5 with a custom stylesheet so the brand does not look like a stock template. Alpine.js handles small interactive pieces (search suggestions, notification badge, chatbot box) without spinning up a full SPA. Leaflet draws market maps without a paid map key. Chart.js appears on the admin reports page.

5. How the code is organised

The layout follows normal Laravel practice. HTTP enters through routes, controllers decide what to load, models talk to MySQL, and Blade renders HTML. Shared logic that does not belong in a controller sits in services— mainly order placement and notifications—so those steps are not copy-pasted across customer and guest flows.

5.1 Routes

routes/web.php lists the pages people actually hit: home, catalogue, search, cart, checkout, and the three dashboards. Guest cart routes sit outside the customer middleware so someone can add items before logging in. Admin and farmer groups use a role: middleware so a customer URL cannot open an admin screen by accident. routes/api.php only exposes simple product and market lists for possible later clients; the shop itself does not depend on them.

5.3 Models

Models under app/Models map to tables. The important relationships are the usual ones: a user may own a farmer profile; products belong to a farmer and a market; cart items point at products; orders keep item snapshots so later price edits do not rewrite history. Helpers on Product (for example canPurchase()) keep “is this buyable right now?” in one place instead of repeating stock checks in every form.

5.4 Services

OrderService is where cart lines become real orders. If the basket mixes two stalls, the service splits them so each farmer gets their own order. Stock is checked again at that moment. NotificationService writes in-app alerts so farmers and customers see status changes without email being mandatory in local demo mode.

5.5 Views and layouts

Public pages use layouts/app.blade.php (navbar, footer, toasts, mobile dock, shop script). Customer, farmer, and admin panels use their own layouts so the side navigation stays role-specific. Cards for products and farmers live in resources/views/partials/ so home, about, and catalogue stay consistent.

5.6 Front-end scripts

home.js drives the harvest calendar modal, month switching, and the small motion helpers on the landing page. It also keeps the calendar usable when dark mode is on by pairing with CSS that forces readable colours on the calendar card and popup.

shop.js is the shopping layer. Forms marked data-ajax-cart post with fetch, show a toast, and update the bag badge. The products filter form uses data-live-filter; changing a select or typing in search reloads only the grid HTML from the server. On phones, a filter drawer and bottom dock keep navigation close to the thumb.

5.7 Stylesheet

Almost all visual branding sits in marketlink.css: colours, cards, dark theme overrides, footer contrast, harvest calendar paper card, toasts, and the mobile dock. Dark mode flips a data-theme attribute on <html>. A few surfaces (login card, harvest modal, calendar grid) stay light on purpose so text never disappears against a dark background.

6. Main user flows (mapped to code)

6.1 Browse and filter products

Route products.index hits ProductController@index. Filters come from the query string. If the request is AJAX (or partial=1), the controller returns products/_grid.blade.php instead of the full page. shop.js swaps that HTML into #productResults and updates the browser URL with history.replaceState so refresh still keeps the filters.

6.2 Add to cart without leaving the page

Product cards and the product detail form post to CartController. When the request asks for JSON, the controller replies with ok/message/count. shop.js reads that and updates every [data-cart-badge]. Guests use session storage; logged-in customers use the carts table. AppServiceProvider shares the count into the navbar and mobile dock on each full page load.

6.3 Checkout

Customer checkout is OrderController@create / @store with the Blade form in orders/place.blade.php. Guest checkout uses the guest routes and a similar form. Both end in OrderService. The place page warns when more than one stall is in the cart, because one pickup window is applied across the resulting orders.

6.4 Farmer order desk

After an order exists, FarmerDashboardController methods move it through accept, decline, ready, and complete. Those actions are ordinary POST forms on the farmer order screens—not AJAX—because a full refresh is fine in a back-office queue and easier to audit.

6.5 Admin moderation

AdminDashboardController covers approvals, catalogue edits, review moderation, announcements, FAQs, settings, and CSV export. Farmer delete / suspend sits here as well so a bad stall can be removed without hunting through the database.

6.6 Harvest calendar on home

The calendar markup is in home.blade.php. Behaviour is entirely client-side in home.js (month chips, event days, modal HTML injected into #harvestEventModalRoot). Grower hints for the modal come from a JSON script tag filled by HomeController. CSS keeps the modal and “Coming up” rows readable in dark theme.

6.7 Live search

The navbar form posts to /search. While typing, Alpine calls /search/suggest and shows a short dropdown. A “See all results” link is there when the query is long enough.

7. Database picture

Migrations under database/migrations create the tables. In short: users and roles; farmer_profiles; markets; categories and products; carts and cart_items; orders and order_items; reviews; favorites; notifications; announcements; faqs; settings. Seeders fill demo markets, stalls, products, and login accounts so a marker can click through without inventing data.

8. Security that is actually in the code

  • Passwords go through Laravel’s hasher, not plain text.
  • Blade escapes output by default; CSRF tokens sit on forms and on AJAX headers.
  • Role middleware walls off customer / farmer / admin URLs.
  • Validation rules reject empty or absurd quantities before stock is touched.
  • Login, contact, and chatbot routes are throttled to slow down spam.
  • Keeping payment offline avoids storing card data in this project.

9. UI notes worth mentioning in a viva

Dark mode caused a few contrast bugs early on (light text on light panels, or dark text on the dark footer). Those were fixed in CSS rather than by rewriting every Blade file. The harvest calendar stays on a cream “paper” card in dark mode so day numbers and the popup stay readable. Footer links are forced to light colours because the footer background is always dark. On small screens the products filters collapse into a drawer and a bottom dock mirrors common phone apps.

10. Install steps (local / XAMPP)

  1. Copy the project into htdocs (example path: C:\xampp\htdocs\marketlink-techwiz-7).
  2. Copy .env.example to .env and set the database name/user/password.
  3. Run composer install.
  4. Run php artisan key:generate.
  5. Create the MySQL database, then php artisan migrate --seed.
  6. Run php artisan storage:link.
  7. Start Apache and MySQL. Open http://localhost/marketlink-techwiz-7/public/.

12. What we did not build (on purpose)

  • Card or wallet payments.
  • Delivery tracking.
  • A full React SPA; Blade + small JS kept the stack simpler for this brief.
  • A “smart” chatbot—answers are keyword FAQ matches managed by admin.

13. Suggested demo script for markers

  1. Guest: open Products, change a filter, add an item, watch the bag badge change without a full reload.
  2. Guest or customer checkout: choose a pickup slot; show the pay-at-stall message.
  3. Farmer login: accept an order, mark ready, then complete.
  4. Admin login: approve a farmer or post an announcement; open reports if time allows.
  5. Toggle dark mode on About and on the home harvest calendar to show contrast handling.
  6. Shrink the browser: show the mobile dock and product filter button.

14. Closing

MarketLink is a pickup-first market platform: catalogue and reservations online, money and collection offline. The codebase is standard Laravel with a thin layer of JavaScript for shopping speed and a single CSS file for brand and dark mode. The sections above should be enough to explain both the product idea and where to look in the repo when someone asks “which file does the cart?” or “where do orders get split by stall?”
